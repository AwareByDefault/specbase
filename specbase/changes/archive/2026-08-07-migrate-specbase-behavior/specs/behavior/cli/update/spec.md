## ADDED Requirements

### Requirement: Update refreshes an existing project and never sets one up
**ID:** refresh-only-what-exists
The update command SHALL run only inside an initialized store and SHALL refresh
only what the project already has. When the store holds no configured tool it
SHALL change nothing and SHALL direct the user to the initialization command. It
SHALL never configure a tool the project has not already configured.

#### Scenario: A store with no configured tool is left alone
**ID:** no-configured-tools
- **WHEN** a user runs update in an initialized store where no tool is configured
- **THEN** no artifact is written or removed
- **AND** the output directs the user to the initialization command

#### Scenario: An unconfigured tool stays unconfigured
**ID:** unconfigured-tool-not-added
- **WHEN** update runs in a project where some supported tools are configured and
  others are not
- **THEN** only the configured tools' artifacts are refreshed

### Requirement: A newly present tool directory is reported, not adopted
**ID:** new-tool-directories-reported
The update command SHALL report supported AI tools whose configuration
directories are present but which the project has not configured, naming the
command that would add them, and SHALL proceed with the configured tools only.
Several such tools SHALL be reported in one consolidated message, and nothing
SHALL be said when there are none.

#### Scenario: One new tool directory is named
**ID:** new-tool-reported
- **WHEN** update finds a supported tool's configuration directory for a tool the
  project has not configured
- **THEN** it names that tool and points at the initialization command
- **AND** it does not configure the tool

#### Scenario: Several new tools share one message
**ID:** several-new-tools-one-message
- **WHEN** update finds more than one such tool
- **THEN** it emits a single consolidated message naming all of them

#### Scenario: Nothing new means nothing said
**ID:** no-new-tools-silent
- **WHEN** every detected tool directory belongs to a configured tool
- **THEN** no tool-detection message is displayed

### Requirement: A tool counts as configured by either artifact kind
**ID:** configured-tool-detection
The update command SHALL treat a tool as configured when the project holds
managed skills for it or managed command files for it, and SHALL then apply the
same version, profile, and delivery synchronization to it as to any other
configured tool.

#### Scenario: A commands-only installation still counts
**ID:** commands-only-tool-configured
- **GIVEN** a tool with generated command files and no generated skills
- **WHEN** update runs
- **THEN** the tool is treated as configured and synchronized

### Requirement: Update runs on drift and otherwise reports the project is current
**ID:** drift-triggers-refresh
The update command SHALL refresh a tool when its installed artifacts were
generated by an older version, or when those artifacts no longer match the active
profile and delivery setting. When neither holds for any tool it SHALL report the
project as already up to date and change nothing. A forced run SHALL refresh
every configured tool regardless.

#### Scenario: An older generating version triggers a refresh
**ID:** version-drift
- **WHEN** a configured tool's installed artifacts record an older generating
  version, or record none at all
- **THEN** update refreshes that tool's artifacts and records the current version

#### Scenario: Settings drift counts even when templates are current
**ID:** profile-or-delivery-drift
- **GIVEN** every installed artifact is already on the current template version
- **WHEN** the installed files do not match the active profile or delivery
  setting
- **THEN** update treats the project as needing an update rather than current
- **AND** adds and removes files until they match

#### Scenario: A current project is left untouched
**ID:** already-up-to-date
- **WHEN** every configured tool is on the current version and matches the active
  profile and delivery setting
- **THEN** update reports the project as already up to date and writes nothing

#### Scenario: A forced run refreshes everything
**ID:** forced-refresh
- **WHEN** the user forces the update
- **THEN** every configured tool is refreshed even when nothing had drifted

### Requirement: Update synchronizes installed workflows to the active profile
**ID:** profile-sync
The update command SHALL generate artifacts for workflows the active profile
selects but the project lacks, SHALL refresh the artifacts of workflows it
already has, and SHALL delete the artifacts of workflows the profile no longer
selects. It SHALL report which tools it refreshed and how many artifacts it
removed, naming the reason for each removal.

#### Scenario: Missing profile workflows are installed
**ID:** missing-workflows-added
- **WHEN** the active profile selects a workflow the project has not installed
- **THEN** update generates that workflow's artifacts for every configured tool

#### Scenario: Deselected workflows are removed
**ID:** deselected-workflows-removed
- **WHEN** the project holds artifacts for a workflow the active profile no
  longer selects
- **THEN** update deletes that workflow's artifacts, honoring the active delivery
  setting

#### Scenario: The run says what changed and where
**ID:** change-summary-reported
- **WHEN** update completes having changed something
- **THEN** it names the tools it refreshed and the version it wrote
- **AND** reports the count of artifacts removed together with the reason for
  their removal

### Requirement: Update enforces the delivery setting by removing the other artifact kind
**ID:** delivery-sync
The update command SHALL make the installed artifact kinds match the delivery
setting: skills-only delivery SHALL delete generated command files, commands-only
delivery SHALL delete generated skill directories, and both-kind delivery SHALL
keep both. Every deletion SHALL be reported with the setting that caused it.

#### Scenario: Skills-only delivery deletes command files
**ID:** skills-only-removes-commands
- **GIVEN** a project holding generated command files
- **WHEN** update runs with skills-only delivery
- **THEN** those command files are deleted, the skills are refreshed, and the
  count removed is reported with the delivery setting

#### Scenario: Commands-only delivery deletes skill directories
**ID:** commands-only-removes-skills
- **GIVEN** a project holding generated skills
- **WHEN** update runs with commands-only delivery
- **THEN** those skill directories are deleted, the command files are refreshed,
  and the count removed is reported with the delivery setting

#### Scenario: Both-kind delivery keeps both
**ID:** both-keeps-both
- **WHEN** update runs with both-kind delivery
- **THEN** skill artifacts and command files are generated or refreshed together

### Requirement: A governed project is regenerated from its current plane set
**ID:** governed-regeneration
For a project that declares governed planes, the update command SHALL rewrite the
generated skill and command content from the plane set the project's
configuration currently resolves to, so the generated guidance reflects each
plane's declared purpose. A project that declares no plane SHALL receive
generated content identical to the flat, ungoverned output.

#### Scenario: Config plane changes reach the generated guidance
**ID:** planes-refreshed
- **GIVEN** a project whose resolved plane set differs from the planes baked into
  its installed artifacts
- **WHEN** the user runs update
- **THEN** the artifacts are rewritten with awareness of the currently resolved
  planes and their declared purposes

#### Scenario: A flat project sees no governed content
**ID:** flat-project-unchanged
- **WHEN** a project that declares no plane runs update
- **THEN** its generated artifacts are byte-identical to the flat output
- **AND** no plane awareness is appended

### Requirement: The first update after an upgrade migrates the project once
**ID:** one-time-migration
The update command SHALL detect a project that holds generated workflow artifacts
but no recorded profile preference, and SHALL record a custom profile holding
exactly the recognized workflows installed across all its tools, taking their
union and ignoring artifacts it does not recognize. Migration SHALL run once,
without prompting, SHALL report what it recorded, and SHALL by itself add or
remove no workflow.

#### Scenario: The recorded profile is the union of what is installed
**ID:** union-of-installed
- **GIVEN** a project whose tools hold different sets of generated workflow
  artifacts and no recorded profile preference
- **WHEN** the user runs update
- **THEN** the recorded workflow list is the union of the recognized workflows
  found across those tools
- **AND** the run refreshes templates without adding or removing a workflow

#### Scenario: User-authored artifacts are ignored while scanning
**ID:** unrecognized-artifacts-ignored
- **WHEN** migration scans the installed artifacts
- **THEN** only recognized workflow names are recorded
- **AND** user-authored skills and commands are left out of the recorded list

#### Scenario: The recorded delivery matches what is installed
**ID:** migrated-delivery-matches-artifacts
- **WHEN** migration records the profile
- **THEN** the recorded delivery reflects which artifact kinds the project
  actually holds

#### Scenario: Migration happens only once
**ID:** migration-is-once-only
- **WHEN** the user runs update again after a migration
- **THEN** no further migration is performed and the recorded preference is used
  as it stands

#### Scenario: A project with no artifacts is not migrated
**ID:** no-migration-without-artifacts
- **GIVEN** no recorded profile preference and no generated workflow artifacts
- **WHEN** the user runs update
- **THEN** no migration is performed and the default profile applies

### Requirement: Oh My Pi artifacts are refreshed in its own layout
**ID:** oh-my-pi-refresh
When Oh My Pi is a configured tool, the update command SHALL refresh its skills
with the current templates and SHALL write one command file per workflow in the
active profile under Oh My Pi's own directories, creating a missing command file
and overwriting an existing one, with every slash-command reference in the
hyphen form Oh My Pi resolves from the filename.

#### Scenario: Oh My Pi skills are refreshed
**ID:** omp-skills-refreshed
- **WHEN** update runs with Oh My Pi configured
- **THEN** its skill files are rewritten from the current templates with
  hyphen-form command references

#### Scenario: Oh My Pi command files are written for every active workflow
**ID:** omp-commands-written
- **WHEN** update runs with Oh My Pi configured
- **THEN** a command file exists under its commands directory for each workflow
  in the active profile, created when absent and overwritten when present

### Requirement: The refreshed archive command still takes an optional change identifier
**ID:** archive-argument-support
The archive workflow artifact the update command refreshes SHALL keep accepting
an optional change identifier from the user. Given one, it SHALL instruct the
agent to validate the identifier against the listed changes and to stop early
when it names nothing archivable. Given none, it SHALL instruct the agent to
infer the change from context and to prompt from the listed changes when the
choice is ambiguous.

#### Scenario: An identifier is validated before use
**ID:** archive-with-identifier
- **WHEN** a user invokes the refreshed archive command naming a change
- **THEN** the artifact instructs the agent to validate that name against the
  listed changes and to fail fast when it matches no archivable change

#### Scenario: No identifier falls back to context and a prompt
**ID:** archive-without-identifier
- **WHEN** a user invokes the refreshed archive command naming no change
- **THEN** the artifact instructs the agent to infer the change from context
- **AND** to prompt the user from the listed changes when that is ambiguous
